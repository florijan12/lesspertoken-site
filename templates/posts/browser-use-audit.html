browser-use is one of the most cost-aware agent codebases we have read. It still has one leak: run it on Claude through OpenRouter or Amazon Bedrock and every step pays full price for the whole history, screenshots included. Turning the cache on should cut that bill by more than half.

Part {{ post.part }} of a series on spending less per token. Part 2 audited GPT Researcher; part 1 explains caching if you're new to it.

The project and how we checked it

browser-use lets an AI agent drive a real browser: it looks at the page (as text and as screenshots), writes a step of code, runs it, and repeats until the task is done. A single task can take dozens of steps, and every step sends the conversation so far back to the model. That makes the prompt cache the most important cost setting in the whole project.

We ran our free LLM cost audit skill on commit 94784c1 (24 November 2026). The scanner found almost nothing, because browser-use calls models through Pydantic AI rather than a provider SDK, so we read the agent loop and the model setup by hand, along with the Pydantic AI version it pins (2.66.0). We did not run the agent; the numbers below are estimates, and we say what they rest on.

What it already does well

  • Screenshot pruning that keeps the cache intact. Old screenshots are dropped 18 at a time instead of one per step, so the cached prefix stays identical between prunes. A comment in the code explains why: pruning every step turned each request into a cache miss on their own benchmark.
  • Caching switched on for Claude on the direct Anthropic API. Another comment records the old state: "cache_read was always 0".
  • Compaction of long histories, on the server where the API supports it and with a summary elsewhere.
  • The end-of-run judge reuses the cache by resending the run's last request instead of a fresh prompt.

This is careful work. The leak below is the kind that survives careful work, because it only shows up on routes the team doesn't use day to day.

1. Claude on OpenRouter or Bedrock never caches

When browser-use builds the agent, it asks for prompt caching in exactly one case: when the provider is anthropic. Claude reached any other way gets no cache setting:

How you pass the modelCache requested?
llm='anthropic:claude-...'Yes
llm='openrouter:anthropic/claude-...'No
ChatOpenAI('anthropic/claude-...', base_url='https://openrouter.ai/api/v1')No
llm='bedrock:...claude...'No

That matters because Claude only caches when asked. OpenRouter's documentation says caching for Anthropic models needs cache_control breakpoints, while OpenAI models cache automatically. Bedrock's Converse API works the same way, with cachePoint blocks. Pydantic AI knows how to add both, but only when the cache setting is on.

So on those routes, every step re-bills the system prompt, the tool definitions, the whole history and up to 20 screenshots at the full input price. The project's own benchmark comment puts the average step at about 39,000 input tokens.

The fix in browser-use (agent/loop.py, build_agent)

name = model if isinstance(model, str) else getattr(model, 'model_name', '')
if system == 'anthropic' or (system in ('openrouter', 'bedrock') and 'claude' in name.lower()):
    if 'cache' not in own:
        settings['cache'] = True

The workaround today: pass the model with caching on

from pydantic_ai.models.openrouter import OpenRouterModel

agent = Agent(task=task, llm=OpenRouterModel('anthropic/claude-sonnet-5.5', settings={'cache': True}))

On Bedrock, the same works with BedrockConverseModel(..., settings={'cache': True}). Check that cache_read tokens show up in the usage after a few steps.

2. A smaller one: the judge runs after every task

By default, browser-use sends one more request after each run to judge whether the task succeeded. On cached routes that's cheap, because it reuses the run's prefix. On the uncached routes above it's billed in full, and if the cached judge fails, the fallback sends up to 120,000 characters of trace plus screenshots as a fresh prompt. If you never read result.judgement, pass judge=False.

Check your own agent for the same thing

  • Look at cache_read (or your provider's equivalent) in your usage data. If it's zero on a model that should cache, nothing else on this list matters as much.
  • If you support several providers, check that the cache setting reaches every route to the same model, not just the one you test on.
  • Count how many images ride along on each request, and whether dropping them rewrites earlier messages.
