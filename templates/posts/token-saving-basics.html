Most LLM bills aren't high because the model is expensive. They're high because the same tokens get sent, generated and paid for again and again. Here are six fixes, each with a worked example, ordered roughly from biggest saving to smallest effort.

Part {{ post.part }} of a series on spending less per token. All examples use {{ ex.model }} at Anthropic's list price ({{ ex.L.list_in }} input, {{ ex.L.list_out }} output per million tokens) unless noted.

First, where the money goes

You pay for three things on every call:

  • Input tokens: your prompt, plus everything you send along with it: system prompt, tool definitions, documents and the whole conversation so far.
  • Output tokens: what the model writes back. On {{ ex.model }} these cost {{ ex.output.ratio }}× as much as input.
  • Repeats: the API has no memory, so the context is sent again on every call. In agents and long chats this is usually the biggest line on the bill.

Every technique below attacks one of these.

1. Cache what you send on every call

If the start of your prompt is identical from call to call (system prompt, tool definitions, a long document), the provider can store it and charge a fraction of the input price when it's reused. On {{ ex.model }}, a cache hit costs {{ ex.L.list_cache }} per million tokens instead of {{ ex.L.list_in }}, just {{ ex.agent.cache_ratio }}% of the normal input price.

Example: a coding agent

50M input and 2M output tokens a month, a realistic month for one developer using an agent every day. Most of the input is the same repository context resent on every step, so 85% of it can come from cache.

SetupMonthly cost

How to get high hit rates:

  • Put everything stable first and everything that changes last. The cache only matches an exact prefix, so one changed character near the top invalidates the rest.
  • Don't put timestamps, request IDs or shuffled tool lists at the top of the prompt.
  • Check your usage data for cache read tokens. If they're a small share of input, your prefix is changing somewhere.

Writing to the cache costs a little more than normal input (1.25× for Anthropic's 5-minute cache), so the table above slightly flatters the result. Anthropic says caching pays for itself after a single cache read.

The simplest router is a rule (short message, known intent: small model). A step up is letting the small model answer and escalating when it says it isn't sure. Test on real traffic before switching, since a cheap wrong answer can cost more than an expensive right one.

3. Ask for shorter answers

Output is the expensive side of the bill, and models are chatty by default: a friendly preamble, a recap of your question, a summary at the end.

Example: an app making 1,000 calls a day

Cutting the average answer from 800 to 300 tokens, by asking for the result only, changes a month's output from {{ ex.output.long_m }}M to {{ ex.output.short_m }}M tokens:

Average answerMonthly output cost
800 tokens{{ ex.output.long }}
300 tokens{{ ex.output.short }} −63%
  • Say exactly what you want back: "Return only the JSON", "Reply with the changed lines as a diff".
  • Set max_tokens as a safety net, not as the main control. A cut-off answer is often useless and gets retried.
  • For code, ask for edits instead of the whole file. Rewriting a 400-line file to change two lines is one of the most common wastes in coding tools.

4. Batch anything that can wait

Anthropic, OpenAI and Google all offer a batch API: you send many requests at once, get results within 24 hours, and pay half price. Evals, nightly reports, tagging a backlog and translating content rarely need an answer in seconds.

Example: a nightly job

20M input and 5M output tokens a month of overnight processing:

On Anthropic, the batch discount stacks with prompt caching. Batch APIs usually run directly with the model maker, so check whether your gateway supports them before planning around it.

5. Stop resending the whole conversation

A chat app that sends the full history on every turn pays for the first message again on turn 2, turn 3 and every turn after.

Example: a 20-turn conversation, 500 tokens per turn

StrategyInput tokens over 20 turns
Resend full history every turn{{ ex.context.full }}
Last 4 turns + a 300-token summary of the rest{{ ex.context.trimmed }} −{{ ex.context.pct }}%
  • Keep recent turns word for word and summarise older ones.
  • For documents, retrieve the relevant sections instead of pasting the whole file.
  • Drop tool results once they've been used. A 5,000-token search result doesn't need to ride along for the rest of the session.

Trimming and caching pull in opposite directions: a summary that changes every turn breaks the cache. For agents with stable context, cache first; for long chats, trim first.
